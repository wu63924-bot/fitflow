# FitFlow Phase 4 完成与验收报告

入口：日历 → 趋势，或 `/history?view=trends`。默认 30 天。仅使用本机 IndexedDB，不产生网络请求。

## 1. 统计指标

- 概览：完成训练次数、总时长、平均每周次数、记录日平均热量、范围内最近体重、体重变化。
- 身体：原始体重、7 日移动平均、首尾记录日期与体重。
- 训练：力量/有氧次数、单次平均时长、最长一次、频率柱状图、总力量容量、每周容量、肌群涉及次数。
- 动作：动作选择、每次最佳完成重量、最佳组、该动作单次容量及历史表。
- 有氧：次数、总时长、平均时长、按运动类型分别汇总有记录的距离。
- 营养：记录日数、平均热量/蛋白质/碳水/脂肪、每日热量和蛋白质图、达到当前蛋白质目标的记录日数。

## 2. 分析层组织

`analyticsService.ts` 进入页面或切换范围时读取现有表与营养目标；`analytics.ts` 是可单独测试的纯计算层；`TrendsPanel.tsx` 展示结果；`AnalyticsChart.tsx` 绘制图表。

页面没有逐次 render 扫描数据库。范围请求切换时忽略过期结果，避免较慢的旧查询覆盖新范围。模块通过 lazy import 按需加载，同时纳入 PWA 预缓存。

## 3. 统计口径

| 项目 | 口径 |
| --- | --- |
| 时间范围 | 包含今天的最近 7/30/90/180/365 个本地自然日；半年和一年分别按 180/365 天。 |
| 力量训练 | completed Session，具有有效开始/结束时间与动作数组；按结束日期归属。未完成、无效日期、结束早于开始等记录不计。 |
| 有氧 | completed cardio DailySchedule，具有有效日期、运动类型和正数实际时长。按日历日期归属；不计计划时长。 |
| 每周训练频率 | 完成力量与有氧次数之和 ÷（范围天数 / 7）。 |
| 时长 | 力量 `(endedAt - startedAt) / 60000`；有氧使用实际分钟。平均分母为有效完成训练次数。 |
| 训练频率图 | 7/30 天按日，90/180 天按周，365 天按月；周一为周起点，边界桶只计范围内记录。无训练日为真实 0 次。 |
| 体重 | 范围内真实有效称重记录，按日期排序；首条与末条之差。只有一条时不展示变化值。 |
| 7 日平均 | 当前记录日及前 6 个自然日内实际记录的平均；可使用范围开始前的实际记录形成窗口，不补缺失日期。 |
| 肌群 | 优先 Session 动作的 category/muscle 快照，缺失时查本地 Exercise。每次训练每个肌群最多 1 次，仅包含有有效完成组的动作。 |
| 距离 | 有效非负距离按运动类型分别求和，并标明有距离记录的次数；未填距离不视为 0。 |
| 营养 | 使用 MealItem 历史营养快照和统一 `calculateMealItem`，不依赖当前 Food 数值。 |

## 4. 图表方案

使用本地 SVG，无新增图表依赖。图表响应容器宽度，提供点选、键盘与 44px 高日期选择框，稠密图表可用日期框准确查看值。热量、蛋白质分图展示；体重原始线与 7 日平均线有说明。

## 5. IndexedDB 与备份

Schema 保持 v3，Backup 保持 v3。没有新增统计表、冗余统计数据或持久化偏好。v1/v2 导入流程保持兼容，恢复后再次进入趋势会重新读取数据计算。

## 6. Mock 趋势移除

移除了 `mockTrendSnapshots`、Mock 容量百分比以及体重图假数据回退。停止首次初始化自动写入示例体重，首页与我的身体摘要无记录时也不显示虚构体重/BMI。

已存在的身体记录不会自动删除：旧版本没有“示例/用户记录”来源标记，不能可靠区分。若本机还保留旧版演示体重，可在“我的 → 身体数据”核对后手动删除。

## 7. 空数据与异常

没有训练、体重、营养时展示对应空状态；体重提供“记录体重”，营养提供“记录饮食”。不绘制无数据的假趋势。NaN、Infinity、负重量/次数、异常日期、跳过动作、未完成组、缺失关键字段等在分析层过滤。

当前 BodyRecord 使用日期唯一主键，同日再次保存会替换当日记录。纯计算层若收到重复日期，取最后一条有效记录，避免重复平均。

## 8. 营养平均分母

分母是范围内至少包含一个有效饮食项目的不同日期数。没有记录的日期不视为摄入 0。页面明确显示“X 个记录日 / N 个自然日”。一次真实的零营养记录仍是记录日；空餐次不是记录日。记录不完整时平均只代表已记录摄入。

## 9. 训练容量

`Σ(weight × reps)`，只计算 completed、未跳过、非有氧动作的有效组。重量有限且 0–10000kg、次数为 1–1000 的整数、乘积有限。范围仅用来过滤明显异常值，不是训练建议。体重记录限定正数且不超过 1000kg；饮食份量不超过既有输入上限 10000，单项计算营养不超过 1000000（与既有食物和份量校验上限对应）。总容量与每周图使用同一计算结果，单位为 kg·次。

## 10. 动作表现

按 exerciseId 关联，单次训练的最佳组优先最大完成重量，同重量取最高次数；容量为该动作所有有效完成组之和。同一 Session 中重复出现同一动作合并为一条表现记录。同日不同 Session 保持独立历史。未新增力量评分或估算 1RM。

## 11. 离线验证

生产构建的 App Shell 与包括趋势独立 JS 在内的 16 项静态资源纳入 Service Worker 预缓存。测试中停止隔离预览服务后，刷新、切换统计范围、打开新标签重新访问均可显示训练/体重/营养数据。没有 API 缓存规则。

这是桌面浏览器中的生产 PWA 缓存验收；未在真实手机上安装 standalone PWA 或执行实体设备飞行模式验收。

## 12. 验证结果

- `npm.cmd run typecheck`：通过。
- `npm.cmd run build`：通过，无 chunk size 警告。输出 `web/dist`。
- `node scripts/test-analytics.mjs`：通过。需要 Node 24，使用其 TypeScript stripping 功能，运行时的 ExperimentalWarning 是 Node 接口提示。
- 自动断言：空数据、单次训练、12 次混合训练、20 个饮食记录日、不连续/同日重复称重、异常数据、范围边界、跳过/有氧/未完成组排除、容量、动作合并、快照肌群优先、长范围分桶。
- 浏览器验收：9 次力量 + 3 次有氧 = 12 次；总时长 5h30min；每周 2.8 次；力量容量 4608 kg·次；8 次称重 71→70.3kg；20 个记录日平均 2000kcal/160g蛋白质/250g碳水/60g脂肪，蛋白质达标 20/20。
- 7 天范围重新计算为 4 个饮食记录日、没有训练/称重；90 天与半年按周、一年按月显示。
- 桌面、375px、390px、430px 检查通过；无页面横向溢出；图表读数与动作历史可操作。
- 在隔离站点导入 v1、v2 测试备份，趋势重新计算为 1 个饮食记录日平均 143kcal，不保留上一次 12 次训练结果。
- 同日两次保存体重 80→81kg，只存在一个当日记录。

## 13. 已知边界

- 每日目标没有历史快照：目标线及达标天数明确按当前目标，不代表当时的目标；修改目标不改变实际摄入。
- 肌群依赖已有动作分类与肌群字段，不推测缺失肌群，也不评价刺激量、恢复或健康状况。
- 稀疏记录的连接线用于阅读记录点，不代表补录缺失日期。
- 旧版自动生成的身体记录可能仍在本机或旧备份中；不会擅自删除。
- 已验证浏览器离线启动，实体手机 standalone 模式仍需人工验收。

## 14. 人工验收

1. 在 Web 项目目录运行 `npm.cmd run build`，再运行 `npm.cmd run preview -- --port 4173`（已有服务时使用其地址或空闲端口）。
2. 打开 `/history?view=trends`，确认默认 30 天；依次选择 7天、90天、半年、一年。
3. 将已完成训练的有效组 `重量×次数` 相加，对照总容量；未完成或跳过的组不得增加容量。
4. 选择动作，核对训练日期、最佳完成组、单次容量；点选图表或日期框查看数值。
5. 在部分日期记录饮食，确认记录日数与平均分母一致；增加未记录日不会改变记录日平均。
6. 间隔数天记录体重，对照原始点及 7 日窗口平均；同日再次保存应只保留最新值。
7. 浏览器分别使用 375/390/430px 视口检查图表、历史表和控件。
8. 成功访问一次以后断网、刷新并重新打开，确认三类统计仍可查看；真实手机也请完成此步骤。
9. 在独立测试浏览器导入旧备份，重新进入趋势，确认结果来自恢复数据。导入会替换该浏览器当前数据，正式数据应先备份。

Phase 4 到此结束。
